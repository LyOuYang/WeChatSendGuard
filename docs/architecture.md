# WeChatSendGuard v1 Architecture

## Scope

This release is a native Windows 10/11 x64 desktop utility. Its single purpose is to add a deliberate confirmation before a message is sent from the supported Weixin desktop UI. The first production release is `1.0.0`.

Windows is the only implementation target in this release. The domain, UI, and platform boundaries are intentionally portable so that later macOS and Linux implementations can reuse the product behavior without copying the Windows integration code.

## Layering

```text
desktop-app (composition, lifecycle, command handling)
    |
desktop-ui (Slint views, view models, no OS calls)
    |
guard-core (rules, settings contract, state machine, audit models)
    |
platform-api (traits and test doubles)
    |
platform-windows (Win32, UI Automation, tray, startup, input injection)
```

Dependencies only point downward. `guard-core` must not know about Weixin, Win32, Slint, a registry key, or a specific file location. `desktop-ui` consumes state and emits intent; it cannot inject input or inspect another application's UI. `platform-windows` is the only layer permitted to use Windows APIs.

## Runtime Flow

1. `platform-windows` receives a keyboard event and reads only its cached foreground context on the hook callback path.
2. `desktop-app` asks `guard-core` to evaluate the current rule set.
3. A pass-through decision lets the original key continue. A blocking or confirmation decision suppresses it.
4. For confirmation, `guard-core` creates one pending attempt containing the trusted window, process, target kind, normalized title, key type, and expiry.
5. `desktop-ui` presents the matching confirmation mode. It never stores a draft preview.
6. After user confirmation, `platform-windows` refreshes the foreground context. `guard-core` permits injection only when it is still the same trusted process, window, target kind, normalized title, and focused editor.
7. Only then may `platform-windows` restore editor focus and emit one marker-tagged `Enter` through `SendInput`.

No message text, clipboard content, screenshot, Weixin database, network request, DLL injection, or process memory access is part of the architecture.

## Configuration Contract

Settings remain at `%LocalAppData%\\WeChatSendGuard\\settings.json`. The persisted schema remains `schemaVersion: 2`; application version and schema version are separate. The Rust implementation accepts the existing camel-case JSON field names and Pascal-case enum values generated by the current .NET version, then sanitizes values using the same bounds and list rules.

Settings changes are written through a same-directory temporary file and replacement operation. Invalid JSON falls back to safe default settings. List changes and the protection on/off switch are applied and persisted immediately; other setting changes are committed only after an explicit save action, preserving current UX semantics.

Audit logs remain best-effort JSON Lines under `%LocalAppData%\\WeChatSendGuard\\logs`. They contain only timestamp, protected-chat ID when applicable, event type, and result. They never contain a chat title or draft text.

## Windows Boundary

The initial `platform-windows` implementation owns:

- low-level keyboard hook and injected-event marker;
- foreground-window observation and trusted executable verification;
- UI Automation read-only context lookup for the known Weixin controls;
- `SendInput` with architecture-size validation;
- tray menu, notifications, and current-user startup registration;
- atomic file replacement and audit-log retention.

Every call that reaches an external process is fail-closed: lack of trust, missing compatibility metadata, elevation mismatch, stale UI Automation elements, or failed revalidation must not result in input injection.

## UI Boundary

Slint is the production UI toolkit. The current Windows interface is the visual and behavioral source of truth: compact three-section settings navigation, restrained WeChat-green status language, separate protected/exemption lists, and a dedicated confirmation dialog. The settings shell is visibly elevated from the desktop surface, and the confirmation dialog is centered over the original trusted target window when its position is available. The long-press progress interaction remains a first-class confirmation mode.

The `desktop-ui` crate will contain only Slint markup, view-model state, localization strings, and intent callbacks. Platform services are supplied as narrow interfaces by `desktop-app`.

## Future Platform Adaptation

macOS and Linux do not reuse `platform-windows`. They implement the `platform-api` contracts and preserve the same `guard-core` decisions, settings JSON, audit schema, and Slint UI behavior. Exact requirements and non-goals are in [platform-adapter-contract.md](platform-adapter-contract.md).

## Packaging Goal

The Windows installer is a signed per-user native package containing one Rust application and the Slint runtime. It must be measured as part of each release and remain at or below 15 MB for the x64 installer unless a reviewed release exception records the reason. No system runtime or .NET installation is required for end users.
